## 2. Наблюдаемые сбои (за один день эксплуатации)

### 2.1. После перезагрузки ВМ кластер не поднимается
**Симптом:** все базы отдают 503, в списке процессов нет `rmngr`, порт 1541 закрыт.
**Факт:** `ragent` живой, `srv1cv8.service` active, `systemctl restart srv1cv8` чинит.
**Вопрос:** как сделать запуск детерминированным?

### 2.2. «Could not find an available working process»
**Симптом:** сразу после перезапуска службы 1С:
```
1C:Enterprise 8 application error: Error executing query
by reason: Could not find an available working process on 1C:Enterprise server.
Attempts: 5, interval: 1000 milliseconds.
```
**Факт:** `rphost` появляется позже `rmngr`; в момент ошибки `rphost = 0`.
**Вопрос:** как не отдавать клиентов до готовности рабочего процесса?

### 2.3. Рассинхрон пароля роли PostgreSQL и инфобазы
**Симптом:** база перестаёт открываться (web/тонкий/толстый клиент), при этом публикация и кластер в порядке.
**Лог PostgreSQL:**
```
ВАЖНО: пользователь "usr_<db>" не прошёл проверку подлинности
ПОДРОБНОСТИ: Пароль не подходит для пользователя "usr_<db>"
```
**Факт:** возникает после перезапусков службы и после создания базы; лечится
`ALTER ROLE ... PASSWORD` + `rac infobase update --db-pwd=...`.
**Вопрос:** почему теряется и как гарантировать согласованность?

### 2.4. Инфобаза со «своим администратором ИБ»
**Симптом:**
```
rac infobase drop   → Недостаточно прав пользователя на информационную базу <name>
rac infobase update → Информационная база имеет непустой список соединений
```
**Факт:** кластерный админ `dgek` не имеет прав ИБ; учётка админа ИБ неизвестна.
**Вопрос:** правильная последовательность (консоль, `--infobase-user`, pg_hba) без правки реестра.

### 2.5. «Отключить всех» не завершает сеансы
**Симптом:** задание «Отключение всех пользователей 1С» завершается ошибкой или сеансы возвращаются.
**Факт:** фоновые задания 1С перезапускаются сразу после `session terminate`;
плюс в логе задания `sudo: a password is required` (права на скрипт).
**Вопрос:** как гарантированно получить 0 сеансов и не ломать работу?

### 2.6. Ручная правка реестра ломает кластер
**Факт:** попытки удалить блок ИБ из `1CV8Clsto.lst`/`1CV8Clst.lst` (счётчики элементов)
дважды приводили к неработоспособному кластеру; откат — из `/root/reg-*.tar.gz`.
**Вопрос:** какие безопасные альтернативы существуют?

### 2.7. Автовосстановление усиливало аварию
**Факт:** healthcheck считал один таймаут `rac` (10 с) аварией и перезапускал `srv1cv8`
во время ручной операции → двойной перезапуск, длительная недоступность.
**Вопрос:** как отличить «1С ещё стартует» от «1С упала»?

### 2.8. Переиндексация полнотекстового поиска
**Симптом:** после импорта `.dt` — `rphost` 80% CPU, каталог `1Cv8FTxt` растёт на гигабайты,
диск `/` заполнился до 89%.
**Факт:** суммарно индексы занимают ~8,7 ГБ, часть — от удалённых/пересозданных баз.
**Вопрос:** когда отключать полнотекстовый поиск и как безопасно чистить индексы?

## 3. Что уже внедрено (учитывать как исходное состояние)

| Механизм | Поведение |
|---|---|
| `1c-cluster-health.timer` | **Production при проверке 12.11 22:14:** каждые 45 с, без debounce и lock; один сбой может запустить серию рестартов. **Локальный фикс, ещё не развёрнут:** grace 180 с, общая `flock`-блокировка, 2 последовательных сбоя, одна попытка `srv1cv8`; RAC-only сбой не вызывает рестарт |
| `1c-heal-bases` | **Production:** автоматически вызывается после восстановления и сбрасывает пароли баз. **Локальный фикс, ещё не развёрнут:** автоматический вызов удалён; сам helper пока небезопасен для ручного запуска |
| `1c-verify-base <ib> <db> <role>` | сброс пароля роли → `rac infobase update` → проверка `psql` |
| `1c-kick-sessions` | разрешает инфобазу через `infobase summary list` (без `cluster list`), права через sudoers |
| `1c-kick-user` | завершает сеансы конкретного пользователя во всех базах |
| `1c-create-base` | создание базы + публикация + автопроверка пароля |
| `1c-republish-base` | публикация `<имя>` с `Ref=<имя инфобазы>` |
| healthcheck-хук | читается из `/etc/1c-portal/mm-hook`, в репозитории секретов нет |

## 4. Вопросы, на которые нужен ответ

1. **Детерминированный старт 1С.** Почему `ragent` поднимается без `rmngr`? Как настроить
   `srv1cv8.service` (зависимости, `ExecStartPost`, `Type`, таймауты), чтобы порт 1541
   открывался гарантированно, а старт базы дожидался готовности `rphost`?
2. **Согласованность паролей БД.** Почему 1С 2342 теряет пароль роли при перезапуске?
   Как сделать идемпотентное восстановление при старте службы (а не только после падения)?
3. **Готовность рабочих процессов.** Как ограничить `rphost` (память, число процессов)
   и не отдавать трафик до готовности? Что смотреть в логах `rphost`/`rmngr`?
4. **Инфобазы с собственным админом ИБ.** Корректный порядок удаления/изменения без правки
   реестра; что делать, если пароль админа ИБ утерян; риски pg_hba `trust`.
5. **Массовое завершение сеансов.** Правильный регламент: `scheduled-jobs-deny`, terminate
   в цикле, проверка 0, снятие запретов; как не блокировать работу пользователей.
6. **Полнотекстовый поиск.** Когда отключать, как чистить осиротевшие `1Cv8FTxt`,
   как ограничить рост диска при импорте `.dt`.
7. **Политика healthcheck.** Как отличить штатный старт от падения; какие метрики
   сделать порогами (503, 1541, rphost, ошибки авторизации PG, свободное место).
8. **Мониторинг и алерты.** Минимальный набор проверок, которые ловят перечисленные сбои
   за 1–2 минуты, без ложных срабатываний.

## 5. Формат требуемого ответа

1. **Таблица причин:** симптом → корневая причина → вероятность (высокая/средняя/низкая) →
   команда/лог для подтверждения.
2. **Решения:** для каждой причины — конкретное изменение (unit-файл, скрипт, параметр 1С,
   настройка PostgreSQL), с ожидаемым эффектом.
3. **План внедрения по приоритету:** сначала то, что убирает простой (P1), затем устойчивость (P2),
   затем красота/метрики (P3); для каждого шага — риск и способ отката.
4. **Готовые фрагменты:** systemd unit, sudoers, bash-скрипты, параметры `rac`/`1cv8`.
   Без реальных паролей — только плейсхолдеры `<...>`.
5. **Чего делать нельзя:** правка `1CV8Clst*.lst` вручную, перезапуск кластера по одному сбою,
   удаление БД при живых сеансах, `trust` в `pg_hba.conf` на постоянной основе.

## 6. Ограничения и требования

- Не предлагать решения, требующие остановки всех баз более чем на 2 минуты без окна обслуживания.
- Учитывать, что часть баз может быть в момент разбора активна.
- Любые изменения должны быть проверяемыми (команда проверки + ожидаемый вывод).
- Соблюдать осторожность с секретами: в ответах — только плейсхолдеры.
