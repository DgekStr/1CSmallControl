# Итог диагностики производительности 1С — 14.11.2026

> **Важно про контекст замеров (уточнение 14.11.2026).** Цифры ниже — про **наш тестовый контур**
> на старом железе с виртуальными дисками. Это не универсальная картина рынка: у большинства
> клиентов уже SATA SSD (**1 000–5 000 fsync-IOPS**), где вход занимает 10–25 секунд, а на NVMe — 3–5 секунд.
> Вывод «узкое место — диск» остаётся верным, но масштаб проблемы зависит от конкретного железа;
> точку ставит замер IOPS при диагностике.


**Статус:** точка зафиксирована. Дальнейшие работы по производительности — после переезда на новый сервер (NVMe).

## 1. Главный вывод

Причина медленного входа в 1С (до 2 минут от ввода пароля) и медленного восстановления баз —
**дисковая подсистема виртуальных машин Proxmox: ~25 синхронных операций в секунду (fsync-IOPS)**.

| Тест | Результат |
|---|---|
| Последовательная запись (`dd`, direct, 512 МБ) на `/` | **578 МБ/с** — выглядит нормально |
| Случайная запись с fsync (200×1 МБ) на `sda` | 8 225 мс → **24 IOPS** |
| То же на `sdb` (`/var/lib/pgpro`) | 3 513 мс на 100 МБ → **28 IOPS** |
| Норма для SSD | **1 000+ IOPS** |
| `pg_restore` дампа | **~0,7 МБ/с** (не завершился за часы) |

PostgreSQL на такой подсистеме тратит десятки миллисекунд на каждый `commit`. При входе в базу
1С выполняет сотни таких операций (загрузка конфигурации, сеанс, кэши) → суммарно минуты.
CPU, RAM, сеть при этом свободны — отсюда парадокс «тормозит на ровном месте».

**Почему «сначала было быстро, а потом стало медленно»:** базы выросли (1,7–3 ГБ), I/O-нагрузка
выросла кратно, и система упёрлась в потолок ~25 IOPS, а не в мощность сервера.

## 4. Остаточные риски

| Риск | Оценка |
|---|---|
| `synchronous_commit=off` | при аварии сервера теряются последние ~200 мс транзакций; для текущей нагрузки приемлемо |
| Диски ~25 IOPS | любые тяжёлые операции (restore, реиндексация, обновление конфигурации) остаются медленными |
| Флуд `990364755` | устранён, но вернётся при неправильном порядке старта HASP после ребута — следить за `error.log` |
| Фантомная инфобаза `goncharov` | запись в кластере без БД; удаляется только через консоль 1С |

## 19.11.2026 — страница статистики: 35 с → 0,6 с

**Причина.** `1c-licenses` вызывал `rac cluster list` без авторизации. В 8.3.27 такой запрос зависает на 20–25 с (внутренний timeout 20), и `admin_stats` блокировался на всё это время; второй вызов (`1c-sessions-list`) добавлял ещё ~1 с.

**Исправление.**
- `1c-licenses`: UUID кластера берётся из `IC_CLUSTER` конфига; fallback `cluster list` с timeout 3 с; `session list` timeout 10 с.
- `app.py`: таймауты подпроцессов снижены — лицензии 10 с, список сеансов 15 с (чтобы будущие зависания не блокировали страницу дольше).

**Замеры `/admin/stats` через gunicorn:** было ~35 с; стало **0,56 с** первый запрос, **0,03–0,05 с** при кэше.

**Осталось:** вкладка «Базы» — счётчики по базам ~4–5 с (по одному `infobase info` на базу, кэш 60 с). Не блокирует статистику; при желании оптимизировать параллельным опросом.

## 19.11.2026 (2) — вкладка «Базы»: 4–5 с → 2 с

**Что сделано.** `1c-sessions-count` опрашивает `rac infobase info` по каждой базе **параллельно** (фоновые процессы + `wait`), а счётчики сеансов считаются одним проходом по общему `session list`. Формат вывода не изменился: `<имя> <сеансов> <jobs:on|off>`.

**Замеры.**
| Сценарий | Было | Стало |
|---|---|---|
| 4 базы (скрипт) | 4,07 с | **2,15 с** |
| `/admin?tab=bases&refresh=1` | ~5 с | **2,1–3,4 с** |
| `/admin?tab=bases` (кэш) | — | **0,015 с** |

**Вывод.** Последовательный опрос заменён параллельным; страница статистики — 0,56 с, базы — 2 с, обе с кэшем открываются мгновенно.
