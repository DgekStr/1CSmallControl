## 2. Симптом

- **Если в базу долго никто не входил, первый вход занимает 3–5 минут.** После выхода/повторного входа — быстро (секунды).
- **Важно: так «просыпаются» ВСЕ базы, а не одна.** Это не проблема отдельной базы, а общее поведение сервера/кластера.
- Наблюдается и на PostgreSQL-базах, и на файловых (на эталонном сервере 1С работает с файловыми базами через RDP, Windows Server 2019).

## 4. Рабочая гипотеза (требует проверки)

Наиболее вероятно: **кластер 1С выгружает из памяти неактивные информационные базы** (настройки «вытеснения памяти» / время жизни рабочих процессов / гибернация сеансов), и при первом обращении `rphost` заново загружает конфигурацию и данные базы из PostgreSQL. Для БП 3.0 (большая конфигурация, база 1,7–3 ГБ) это занимает минуты. После загрузки — всё быстро, пока базу снова не выгрузят.

Это объясняет, почему «просыпаются» **все** базы и почему после выхода/входа быстро.

Альтернативы для проверки:
- гибернация сеансов и большой таймаут восстановления;
- «холодный» кэш PostgreSQL;
- медленный первый запрос конфигурации (полнотекстовый индекс, merge `1Cv8FTxt`);
- блокировки на старте сеанса (в т.ч. фоновыми заданиями);
- настройки публикации (`default.vrd`), например отсутствие пула соединений.

## 4.1. Гипотеза пользователя: задержка связана с отрисовкой (видео/RDP), а не с БД

Наблюдение: база загружается, **заголовок окна/формы виден сразу**, но **«картинка» (сам интерфейс) появляется с задержкой — иногда до 30 с**.

Почему это важно: если бы тормозил сервер БД/1С, не появился бы и заголовок — данные и UI пришли бы вместе. Ситуация «сначала заголовок, потом картинка» = **отрисовка на стороне клиента**.

Что проверить:
1. **Эталон через RDP (Windows Server 2019):** отрисовка 1С идёт на сервере, картинка передаётся по RDP. Задержка появления содержимого при живом заголовке — типичный признак медленного RDP-рендеринга (сжатие, отсутствие GPU, узкий канал), а не БД.
   - проверить настройки RDP (графика/RemoteFX/AVC), глубину цвета, сжатие;
   - сравнить с локальным запуском на машине пользователя (без RDP);
2. **Веб-клиент:** UI 1С рисуется в браузере (HTML5/canvas). Проверить:
   - включено ли аппаратное ускорение браузера, драйвер GPU, старый браузер;
   - настройку 1С «использовать аппаратное ускорение» (Параметры → Интерфейс) — попробовать выключить/включить;
   - воспроизводится ли на другом ПК/браузере.
3. **Замер-разделитель:** засечь три момента — (а) ответ сервера/форма, (б) заголовок, (в) полностью отрисованный интерфейс. Если (а) и (б) быстрые, а (в) медленное — причина в отрисовке, не в БД.
4. Сравнить: та же база через **тонкий клиент**, через **веб-клиент** и через **RDP** — где задержка, там и слой отрисовки.

Вывод промпту: подтвердить или опровергнуть, что 3–5 минут — это **две разные проблемы**: (1) «прогрев»/загрузка базы (серверная часть, см. раздел 4) и (2) медленная отрисовка интерфейса (клиент/RDP). Их нужно лечить раздельно и измерять отдельно.

## 5. Задачи агента

### A. Подтвердить/опровергнуть механизм «выгрузки из памяти»
1. Снять текущие параметры кластера и инфобазы (жизнь рабочих процессов, память, гибернация, таймауты):
   ```bash
   RAC=/opt/1cv8/x86_64/8.3.27.2342/rac
   $RAC 127.0.0.1:1545 cluster info --cluster=<UUID> --cluster-user=... --cluster-pwd=...
   $RAC 127.0.0.1:1545 infobase info --cluster=<UUID> --infobase=<UUID> ...
   ```
2. Провести эксперимент: оставить базы на простое, зафиксировать момент выгрузки (память `rphost`, `rac process list`), затем замерить первый вход.
3. Проверить, растёт ли память `rphost` во время «просыпания» и какие операции идут в PostgreSQL (pg_stat_activity во время входа).

### B. Проверить альтернативы
- Включить/снять гибернацию сеансов, посмотреть эффект;
- проверить кэш PostgreSQL и `shared_buffers`;
- проверить, не тормозит ли загрузка конфигурации (размер `.cff`, время первого `DBMSSQL`);
- проверить `default.vrd` (пул, `pool-size`), публикации всех баз.

### C. Предложить и проверить исправление
Варианты (оценить риск/эффект):
- настроить «не выгружать» активные базы / увеличить память рабочих процессов / отключить вытеснение;
- **прогрев по расписанию**: перед началом рабочего дня лёгким подключением «поднимать» базы (healthcheck-warmup);
- увеличить `shared_buffers`/кэш PostgreSQL;
- отключить полнотекстовый поиск/merge на нерабочих базах;
- проверить/убрать лишние фоновые задания.

## 6. Формат ответа

1. Таблица «симптом → причина → вероятность → подтверждающая команда/лог».
2. Решение для каждой причины: конкретное изменение + ожидаемый эффект + откат.
3. План по приоритету: что убирает задержку сразу, что требует окна.
4. Критерии приёмки: первый вход после простоя `< 30 с`, повторный `< 10 с`, все базы.
5. Отдельно указать: какие задержки относятся к **серверу (прогрев БД)**, а какие — к **отрисовке интерфейса (RDP/браузер)**; для второй группы дать настройки RDP/браузера/1С.
6. Запреты: не править реестр `1CV8Clst*.lst` вручную; не останавливать кластер в рабочее время; не менять пароли БД без схемы «проверка → лечение»; секреты только плейсхолдерами.

## 7. Полезные команды

```bash
. /etc/1c-portal/1c-session-admin.conf
RAC=/opt/1cv8/x86_64/8.3.27.2342/rac

# сеансы и процессы
$RAC 127.0.0.1:1545 session list --cluster=$IC_CLUSTER --cluster-user=$IC_CLUSTER_USER --cluster-pwd=$IC_CLUSTER_PWD
$RAC 127.0.0.1:1545 process list --cluster=$IC_CLUSTER --cluster-user=$IC_CLUSTER_USER --cluster-pwd=$IC_CLUSTER_PWD

# память/нагрузка
ps -eo pid,pcpu,rss,etime,comm --sort=-pcpu | head -6
free -h; uptime; df -h /

# PostgreSQL: что делает база во время входа
sudo -u postgres psql -d <db> -Atc "select pid,state,wait_event,now()-query_start,left(query,80) from pg_stat_activity where datname='<db>'"

# публикация
cat /var/www/1c/<имя>/default.vrd
```
