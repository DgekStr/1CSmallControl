# Задание для ИИ-агента: причины задержки запуска баз 1С и план проверки/исправления

> Передать агенту целиком. Секретов в файле нет: пароль sudo/учётные записи подставляет
> оператор; в командах используйте плейсхолдеры `<SUDO_PASS>`, `<IC_CLUSTER_PWD>`.

## 1. Доступ к деплой-серверу (обязательно)

```bash
# SSH на сервер 1С (деплой-сервер, Ubuntu, 192.168.0.5)
ssh -i ~/.ssh/id_ed25519_dgek1c dgek@192.168.0.5

# sudo на сервере (пароль запросит интерактивно)
sudo -S <команда>    # пароль: <SUDO_PASS>

# внешние адреса
#   портал:        https://1c.dgek.ru
#   nginx-прокси:  root@192.168.0.15 (ключ ~/.ssh/id_ed25519)
#   гипервизор:    root@192.168.0.18 (ключ ~/.ssh/id_ed25519_pve2), ВМ 213
```

Ключевые пути и файлы на сервере:

| Что | Путь |
|---|---|
| Портал (Flask) | `/opt/1c-portal` |
| Публикации 1С | `/var/www/1c/<имя>/default.vrd` |
| Креды кластера для скриптов | `/etc/1c-portal/1c-session-admin.conf` |
| Креды БД баз | `/etc/1c-portal/db-creds` (root, 640) |
| Хук MM | `/etc/1c-portal/mm-hook` |
| Healthcheck | `/usr/local/bin/1c-cluster-health` + `1c-cluster-health.timer` (45 с) |
| Heal паролей БД | `/usr/local/bin/1c-heal-bases`, `/usr/local/bin/1c-verify-base` |
| Службы | `srv1cv8`, `ras`, `1c-portal`, `apache2` |

## 2. Симптом (жалоба пользователя)

- Если в базу долго никто не входил, **первый вход занимает 3–5 минут**, при этом в системе
  никто не работает.
- «Выйти и зайти заново» — после этого работает быстро.
- Наблюдается на нескольких базах; нагрузка на сервере при этом почти нулевая.

## 3. Что уже измерено (12.11–13.11.2026)

| Проверка | Результат |
|---|---|
| Вход в портал | 2,4 с |
| Открытие базы → форма входа 1С | **2,1 с** |
| Нажатие «Войти» (`Бухгалтер`/`000`) | **зависает** (в тесте 600 с, форма входа так и осталась) |
| PostgreSQL `pg_stat_activity` по базе | сессии `idle`/`ClientRead`, **блокировок 0** |
| RAM | ~26 ГБ свободно из 29 ГБ |
| Диск `/` | 59 ГБ, занято ~40 ГБ (71%) |
| `rphost` | **постоянно ~190% CPU**, RSS ~4 ГБ |
| Регламентные задания | 2–3 сеанса `BackgroundJob` (`DefUser`) постоянно |
| Лицензии HASP | `Loaded 0 licenses` при старте `hasplm` |
| `error.log` HASP | **42 МБ**, растёт каждые ~5 с: `HASP HL 990364755 does not contain configuration information. Key will be ignored` / `was not added to the list of known keys` |
| Демоны HASP | `aksusbd_x86_64`, `hasplm -c /etc/hasplm/hasplm.conf`, `usbhaspd`, `usbhasp .../B0061DAD-x64.json`, `hasplmd -s` |

**Рабочая гипотеза до проверки:** задержка могла быть связана с выдачей лицензии и/или
перегрузкой `rphost`. Результаты проверки 13.11.2026 ниже: лицензия HASP выдана процессу 1С,
поэтому `Loaded 0 licenses` в Sentinel log само по себе не доказывает потерю 100-user лицензии.
Высокая нагрузка `rphost` и фоновые сеансы остаются вероятной, но не доказанной причиной задержки входа.

## 4. Задачи агента

### A. Доказать/опровергнуть причину
1. Снять тайминги входа **до/после** перезапуска HASP-стека.
2. Проверить фактическую выдачу лицензий: `Loaded N licenses`, записи `LM` в `/var/hasplm/access.log`,
   количество и типы сеансов через `rac session list`.
3. Проверить, что `rphost` 190% CPU — это регламентные задания/полнотекстовая индексация,
   а не зависший сеанс: `top -H`, `rac session list`, `rac process list`, рост каталогов `1Cv8FTxt`.
4. Исключить альтернативы: DNS/обратный резолв при подключении к PostgreSQL (pg_hba использует 127.0.0.1/32 — проверить),
   холодный кэш БД, блокировки, сеть между публикацией и кластером.

### B. Исправить (по согласованию с оператором)
1. **Перезапуск стека HASP** с ротацией лога:
   ```bash
   sudo systemctl restart aksusbd hasplm usbhaspd   # точные unit-имена проверить
   sudo truncate -s 0 /var/hasplm/error.log          # после ротации/бэкапа
   grep -i 'Loaded .* licenses' /var/hasplm/access.log | tail -3
   ```
   Если ключ HASP HL 990364755 неисправен — задокументировать и не пытаться «лечить» его правками.
2. Если фоновые задания мешают: точечно `scheduled-jobs-deny=yes` для нерабочих/тестовых баз
   через `rac infobase update` (только для конкретных баз, не глобально!). Возврат — после проверки.
3. Полнотекстовый поиск: на нерабочих базах отключить; для рабочих — согласовать;
   чистить только осиротевшие каталоги `1Cv8FTxt` (не от активных инфобаз).
4. **Мониторинг:** добавить проверки:
   - `Loaded 0 licenses` в `access.log` → алерт;
   - рост `/var/hasplm/error.log` > 10 МБ/час → алерт;
   - `rphost` CPU > 150% дольше 10 минут → предупреждение;
   - время входа в базу > 30 с (проверка через healthcheck/портал) → алерт.

### C. Не делать
- Не править реестр `1CV8Clst*.lst` вручную (дважды ломал кластер).
- Не удалять БД при живых сеансах; не менять пароли ролей баз без схемы «проверка → лечение».
- Не останавливать `srv1cv8` в рабочее время без окна обслуживания.
- Не «чинить» ключ HASP необратимыми операциями.
- Не публиковать секреты (пароли, хуки) в отчётах и коммитах.

## 5. Порядок работы и отчётность

1. Сначала **только диагностика** (без изменений), с фиксацией таймингов и логов.
2. Гипотеза + план изменений → согласование с оператором.
3. Изменения — по одному, с проверкой после каждого; при сомнении — откат.
4. После каждого этапа: команда проверки + ожидаемый/фактический вывод.
5. Итоговый отчёт: таблица «симптом → причина → что сделано → как проверено → риск/откат».

## 6. Критерии приёмки

| Критерий | Ожидание |
|---|---|
| Лицензии | `Loaded N licenses`, N > 0, ошибок ключа в `error.log` нет |
| Первый вход после простоя | < 30 секунд |
| Повторный вход | < 10 секунд |
| `rphost` CPU в простое | < 50% |
| Мониторинг | алерты на «0 лицензий», рост HASP-лога, долгий вход |

## 7. Полезные команды (шпаргалка)

```bash
# кластер и сеансы
. /etc/1c-portal/1c-session-admin.conf
RAC=/opt/1cv8/x86_64/8.3.27.2342/rac
$RAC 127.0.0.1:1545 infobase summary list --cluster=$IC_CLUSTER \
     --cluster-user=$IC_CLUSTER_USER --cluster-pwd=$IC_CLUSTER_PWD
$RAC 127.0.0.1:1545 session list --cluster=$IC_CLUSTER --infobase=<uuid> \
     --cluster-user=$IC_CLUSTER_USER --cluster-pwd=$IC_CLUSTER_PWD

# лицензии
tail -20 /var/hasplm/access.log
tail -20 /var/hasplm/error.log
grep -c 'Loaded .* licenses' /var/hasplm/access.log

# нагрузка
ps -eo pid,pcpu,rss,etime,comm --sort=-pcpu | head -6
uptime; free -h; df -h /

# PostgreSQL
sudo -u postgres psql -d <db> -Atc "select pid,state,wait_event,now()-query_start from pg_stat_activity where datname='<db>'"

# демоны и таймеры
systemctl status srv1cv8 ras 1c-portal apache2 --no-pager | head -40
systemctl list-timers --no-pager | head -10
```

## 8. Результаты проверки и реализации (13.11.2026)

### Подтверждено

- `usbhaspd` загрузил `ORGL8: 100 Users`; присутствуют три USB-устройства `0529:0001`.
- RAC `process list --licenses` подтвердил `license-type: HASP` и `issued-by-server: yes`.
   В `/var/hasplm/access.log` были записи `Loaded 0 licenses`, а `error.log` содержал ошибки
   распознавания ключа. Эти записи не отменяют фактическую выдачу лицензии процессу 1С.
- При старте 06:57 `aksusbd` начал работу раньше появления устройств от `usbhaspd`; его журнал
   содержит обращения к ещё отсутствовавшим USB-узлам.
- `rphost` потреблял около 181% CPU и 4,2 ГБ RSS; в кластере были два `BackgroundJob`-сеанса.
   Оба сеанса относились к `test` (FTxt 3,1 МБ), имена заданий не сообщались; их CPU-time-current
   был около 23–25. Они не объясняют длительную CPU-наработку `rphost` (около 20 ч за 11 ч).
- FTxt-каталоги: `montes_buh` — 2,3 ГБ, `montes-bp` — 2,3 ГБ, `goncharov2026` — 924 МБ,
   `dgek_db` — 4 КБ. В первых двух недавно обновлялись `files_for_accept/startMergeFiles.dat`,
   что совместимо с merge полнотекстового индекса, но само по себе не доказывает причину CPU.
- Ещё один каталог FTxt 2,6 ГБ не сопоставился с текущим `rac infobase summary list`.
   Это кандидат на осиротевший индекс; он не удалялся и требует отдельной сверки с реестром/бэкапами.

### Проверка после reboot и остановки заданий (13.11.2026)

- По запросу оператора сервер перезагружен в 18:41 MSK. На первом снимке `ragent` был active,
   но `rmngr`/`rphost` и порт 1541 отсутствовали; RAC не подключался к агенту на 1540.
- `1c-cluster-health` дождался grace-периода, зарегистрировал 2 последовательных ошибки и в 18:46
   выполнил ровно один restart `srv1cv8`; в 18:46:21 журнал подтвердил «кластер восстановлен».
   После этого RAC list/process заработали, 1541/1540/1545 слушали, портал `/healthz` вернул 200.
- На старте Sentinel `aksusbd.service` стал inactive, потому что отдельный `haspd.service` уже
   запустил `aksusbd` (журнал: `process already running`). Фактический процесс `aksusbd`, порты
   HASP и USB-устройства были на месте; RAC подтвердил HASP и `issued-by-server: yes`.
- После boot снова возникли 6 `BackgroundJob`-сеансов в `dgek_db`, `montes-bp` и `test`;
   `rphost` достиг 219% CPU и RSS ~4,2 ГБ. `current-service-name` в RAC был пустым, поэтому имена
   конкретных регламентных процедур установить не удалось.
- Учётка `Бухгалтер` прошла проверку прав на `dgek_db`, `goncharov2026`, `montes-bp`; в `test`
   доступ запрещён. В этих трёх базах предыдущий флаг был `scheduled-jobs-deny=off`; установлен
   `on`, исходные значения сохранены в `/var/backups/1c-background-jobs-20261113T155154Z/`.
- Текущие фоновые сеансы были завершены штатно через RAC. После этого `rphost` снизился примерно
   до 30,5% CPU и 1,38 ГБ RSS. Два `BackgroundJob` в `test` запустились снова, потому что его
   расписание осталось разрешённым; без администратора этой ИБ блокировку включить не удалось.
- 100-user JSON не менялся. После reboot RAC снова подтвердил HASP-лицензию; все 3 виртуальных
   устройства видны. HASP, PostgreSQL и пользовательские базы отдельно не перезапускались.

### Развёрнуто

- Установлен readiness helper: перед запуском `aksusbd` systemd ожидает все три HASP USB-устройства
   до 30 секунд; затем `hasplm` стартует после `aksusbd`.
- Добавлено правило `/var/hasplm/error.log`: порог 10 МБ, 7 ротаций, `copytruncate`.
   Проверен logrotate dry-run; сам лог при выкладке не очищался и не вращался.
- Backup 100-user ключа: `/var/backups/1c-hasp-safety-20261113T145927Z/net100-key.json`
   (режим 0600). SHA-256 исходника и копии совпал.
- Ни одна служба HASP или 1С не перезапускалась. PID служб до/после совпали, RAC после выкладки
   продолжал подтверждать HASP-лицензию. Изменения systemd вступят в действие при следующем штатном
   старте служб/сервера.

### Не проверено / осталось

- Вход пользователя после выкладки и критерии `<30 с` / `<10 с` не измерены.
- Текущая высокая нагрузка заметно уменьшилась после блокировки расписаний в трёх базах, но конкретные
   задания не идентифицированы. Для постоянного запрета в `test` нужна учётка администратора этой ИБ;
   иначе его фоновые сеансы будут запускаться снова.
- `error.log` продолжал содержать сообщения Sentinel; его размер при проверке был около 43 МБ.
   Ротация должна пройти штатным `logrotate.timer`; ошибки ключа вручную не исправлялись.
- Автоалерты для CPU/часового роста лога и замер фактической длительности входа не внедрялись.
