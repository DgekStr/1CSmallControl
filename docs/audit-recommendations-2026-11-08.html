S-08 Критично Обход прав доступа к базам через сегменты «..» в шлюзе /WEB/

app.py:466-481 (web_gate), Apache vhost 127.0.0.1:8081

Проверка прав выполняется для slug из URL, а rest (<path:rest>) без изменений добавляется к пути запроса к Apache 8081. Werkzeug не удаляет сегменты .. (включая %2e%2e и ..%2F), а Apache нормализует путь перед сопоставлением Alias. Подтверждено на сервере (in-process тест маршрутизации на Flask 3.0.2 и GET к 8081): /WEB/demo/../test/ → slug='demo', rest='../test/'; Apache 8081 отвечает 200 стартовой страницей базы test. Клиент с доступом к одной базе получает веб-клиент любой опубликованной базы (включая чужие песочницы); аудит пишет только slug своей базы.

Исправление. В web_gate: разбить rest по /, отклонять сегменты '', '.', '..', символы \, \x00; альтернативно norm = posixpath.normpath('/WEB/%s/%s' % (slug, rest)) и требовать norm == '/WEB/%s' % slug or norm.startswith('/WEB/%s/' % slug), иначе _web_denied(slug, 'not-found', 404). То же для web_gate_redirect. На Apache 8081 дополнительно можно включить отдельные <Location> с Require all denied для всего, кроме /WEB/<slug>/. Покрыть тестами (4 варианта кодирования).

P-01 Вынести трафик веб-клиента 1С из Python

Сейчас каждый из 13 тыс. запросов в день проходит nginx → Apache → gunicorn (Python, GIL, 64 потока) → Apache 8081 → 1С. Это добавляет два hop-а, занимает потоки на long-poll (60 с) и печать (до 300 с), и делает портал единой точкой отказа для работы в 1С (при перезапуске портала веб-клиент падает — в логах Apache «Connection refused» 14:16 и 19:48).

Схема. nginx на .15: location /WEB/ { auth_request /_portal_auth; proxy_pass http://192.168.0.5:8082; }; location = /_portal_auth { internal; proxy_pass http://192.168.0.5:80/auth/check; proxy_set_header X-Original-URI $request_uri; proxy_pass_request_body off; }. Портал: /auth/check читает cookie сессии и slug из X-Original-URI (с нормализацией — S-08), отвечает 200/403/401 и кэшируется nginx 30 с по cookie+slug. Apache на .5: новый vhost 192.168.0.5:8082 c теми же публикациями и Require ip 192.168.0.15. Баннер регламентных работ — sub_filter '</body>' '<script src="/static/maint.js" defer></script></body>' только для location ~ ^/WEB/[^/]+/$. Ожидаемый эффект: p50 /WEB/ ≈ время 1С без надбавки Python, устойчивость к перезапускам портала, освобождение потоков gunicorn. Сначала добавить %D в LogFormat vhost-а 8081, чтобы измерить вклад портала до/после.

P-03 Коллектор rac и снижение числа процессов

P-05 Резервное копирование быстрее и надёжнее

Текущие ≈2,5 мин на 1 ГБ базы: однопоточное сжатие zlib в pg_dump -Fc на медленном ядре плюс запись на CIFS. PostgreSQL 16 поддерживает --compress=zstd:3/lz4 и параллельный формат каталога -Fd -j 3. Дамп во временный локальный каталог (на /var/lib/pgpro свободно 23 ГБ), проверка pg_restore -l, затем перенос на CIFS (tar или каталог). Ожидаемо в 3–5 раз быстрее при меньшей нагрузке на CPU в рабочее время (ручные запуски днём наблюдались 15:08–18:38).

P-06 Сервер 1С: rphost 100 % одного ядра

В момент снимка (воскресенье 21:08) rphost потреблял 101 % CPU и 4,4 ГБ RSS более часа при 3–4 простаивающих сеансах — вероятно, регламентные/фоновые задания (в том числе баз test, demo, песочниц). На CPU с низкой частотой это напрямую удлиняет отклик интерактивных сеансов.

Действия. rac session list с cpu-time-current/current-service-name, технологический журнал (события CALL/SCALL по длительности); по умолчанию scheduled-jobs-deny=on для test/demo/песочниц (S-05); ограничить фоновые задания по расписанию; перезапуск rphost в нерабочее время (уже в docs/1c-performance-plan.md). Рассмотреть ограничение памяти рабочего процесса в настройках кластера.

P-07 PostgreSQL (проверить с root)

Конфигурация не читается без root. По памяти процессов shared_buffers ≈ 4 ГБ (20 % RAM — норма для 1С). Проверить: effective_cache_size ≈ 12 ГБ, work_mem 32–64 МБ, maintenance_work_mem 1 ГБ, random_page_cost=1.1 (SSD), checkpoint_completion_target=0.9, wal_compression=on, huge_pages=try, max_connections (сейчас много idle-подключений от 1С), настройки autovacuum для 1С (autovacuum_vacuum_scale_factor=0.02, autovacuum_analyze_scale_factor=0.01, autovacuum_max_workers=4), pg_stat_statements и track_io_timing для поиска тяжёлых запросов; регулярный REINDEX/VACUUM ANALYZE в окно регламентных работ (есть механизм окон).
