# Ускорение интерфейса 1С: план и замеры

Документ фиксирует, что именно тормозит в интерфейсе 1С на этом сервере, что уже
сделано и какие изменения подготовлены. Замеры выполнены 5 ноября 2026 г.

## 1. Что показали замеры

| Проверка | Результат | Вывод |
|---|---|---|
| Кэширование статики 1С | `mod_main_mainform.js` 3,95 МБ и `mod_main_loader.js` 3,79 МБ отдаются с `max-age=3153600` | браузер уже кэширует, со стороны сервера добавлять нечего |
| Сжатие | 84 из 89 ответов 1С приходят в gzip | сжатие уже работает |
| Процессор сервера при открытии базы | пик 10 %, среднее 5 % от 12 ядер (≈0,6–1,3 ядра) | сервер не загружен на полную |
| PostgreSQL при открытии базы | 1 активный запрос, длительность ≈0 мс, блокировок нет | база не является узким местом |
| Частота процессора на гипервизоре | governor = `performance` | частота уже максимальная (2,27 ГГц) |
| Объём загрузки веб-клиента | ~8 МБ JS + 84 запроса на старте | основной вес — клиентская часть |

**Вывод:** узкое место — не кэш и не база, а количество и стоимость запросов при
старте веб-клиента и скорость одного ядра процессора (Xeon L5520, 2,27 ГГц, 2009 г.).

## 2. Что уже сделано на портале

- статика портала отдаётся с кэшем 30 дней и версией в ссылке (`?v=<версия>`);
- включено сжатие ответов портала (html, css, js, json);
- повторная загрузка страницы входа: 2,31 с / 0,68 МБ → **0,61 с / 0,05 МБ**;
- тяжёлые вызовы `rac` кэшируются с фоновым прогревом («Базы» 1,9 с → 5 мс,
  «Статистика» 0,76 с → 30 мс).

## 3. Подготовленные изменения

### 3.1. Безопасный перезапуск сервера 1С

Скрипт `1c-safe-restart.sh`:

```bash
sudo /usr/local/bin/1c-safe-restart.sh check   # только посмотреть состояние
sudo /usr/local/bin/1c-safe-restart.sh apply   # завершить сеансы и перезапустить
```

Порядок: проверка состояния → завершение сеансов → `systemctl restart srv1cv8` →
ожидание кластера → проверка публикации. Без `apply` ничего не меняет.

**Когда запускать:** в нерабочее время, предупредив пользователей. Простой — 1–3 минуты.

### 3.2. Регламентное обслуживание

Рекомендуется раз в неделю (ночью) выполнять `apply` — перезапуск освобождает
накопленную память рабочих процессов и сбрасывает кэши 1С. На этом сервере один
рабочий процесс (`rphost`) с 2,9 ГБ памяти работает больше суток.

### 3.3. Тонкий клиент вместо веб-клиента

Самый большой выигрыш без изменений на сервере:

- тонкий клиент 8.3.27.2342 хранит конфигурацию локально — вместо 8 МБ JS
  загружается только разница;
- запуск и переключение форм заметно быстрее;
- подходит для работы с ЭЦП и оборудованием (там он и так нужен).

Установка: `1c-enterprise-8.3.27.2342-ws` (Linux) или клиент 8.3.27.2342 для Windows,
подключение к порталу, база `base1`.

## 4. Что даст прирост на будущее

| Мера | Ожидаемый эффект | Стоимость |
|---|---|---|
| Перенос ВМ на современный CPU (3+ ГГц, E5 v4 / Silver) | 2–3× на всех операциях | замена железа/хоста |
| Тонкий клиент на рабочих местах | 2–4× на старте и переключении форм | бесплатно |
| Больше ОЗУ серверу (32 ГБ) | запас под кэш 1С и PostgreSQL | планка памяти |
| HTTPS + HTTP/2 на портале | меньше накладных на 84 запроса | сертификат, настройка |

## 5. Что делать не нужно

- включать второй сокет ВМ — 1С не получает прироста, только переподписка CPU;
- менять `range` портов и число рабочих процессов — 1С управляет ими сама,
  при 2–3 одновременных пользователях один процесс оптимален;
- добавлять кэш на стороне портала для `/WEB/` — 1С уже отдаёт всё с кэшем.
